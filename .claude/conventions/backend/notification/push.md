## Rule (어댑터 경계)
- 푸시 SDK는 `app/infrastructure/push/`에만. `firebase_admin` import가 이 폴더 밖에 나가지 않는다.
- 서비스는 `app/domain/ports/push_sender.py`의 `PushSender` Protocol만 안다. 구현 교체(FCM→APNs 직접)가 서비스 수정 없이 되어야 한다.
- 개발·테스트용 `LoggingPushSender`(로그만 남김) 구현을 둔다. 실기기 없이 알람 흐름을 검증할 수 있어야 한다.

## Rule (전송 시점)
- 푸시는 DB 커밋 이후에 발송한다. 커밋 전 발송은 롤백 시 유령 알림을 만든다.
- 푸시 실패가 측정값 저장 트랜잭션을 롤백시키지 않는다. 저장은 성공으로 두고 발송 실패를 별도 기록한다.
- 상태 전이가 일어난 순간에만 발송한다. 같은 상태 유지 중 heartbeat마다 발송하지 않는다.
- ALARM은 사용자 명시 해제 전까지 자동 해제 알림을 보내지 않는다.

## Rule (신뢰성)
- 푸시는 best-effort다. 도달을 보장하지 않는다 — 안전 기능을 푸시 도달에 의존시키지 않는다(노드 로컬 부저·사이렌이 1차 방어).
- 발송 시도·결과를 DB에 기록한다: `alert_id`, `token`, `attempt`, `status`, `error_code`, `sent_at`.
- 재시도는 지수 백오프 + 상한. 무한 재시도 금지.
- 재시도 대상은 일시적 실패(네트워크·5xx·`UNAVAILABLE`)만. 영구 실패(무효 토큰)는 즉시 중단하고 토큰을 정리한다.
- 발송에 타임아웃을 건다. RPi에서 무응답 HTTP가 수신 루프까지 지연시키면 안 된다.

## Rule (토큰 관리)
- 기기 토큰은 별도 테이블. 사용자/기기 단위로 여러 개를 허용한다.
- FCM이 `UNREGISTERED`·`INVALID_ARGUMENT`를 반환한 토큰은 비활성 처리한다. 방치하면 실패율이 계속 쌓인다.
- 토큰 등록 endpoint는 멱등이다. 같은 토큰 재등록이 중복 행을 만들지 않는다.
- 토큰은 비밀값으로 취급한다 — 로그에 전체를 남기지 않고 앞뒤 일부만 남긴다.

## Rule (페이로드)
- 알림 본문에 사용자가 즉시 판단할 정보를 넣는다: 장비 식별, 상태, 감지 시각.
- 원시 센서 수치를 본문에 나열하지 않는다. 상세는 앱이 API로 조회한다.
- `data` 페이로드에 `alert_id`를 넣어 앱이 딥링크로 상세 화면에 갈 수 있게 한다.
- 알람 등급에 따라 채널·우선순위를 나눈다. ALARM과 FAULT를 같은 채널로 보내지 않는다.

## Rule (자격증명)
- 서비스 계정 키 파일을 repo에 커밋하지 않는다. 경로를 설정값으로 주입한다.
- 키 파일 권한은 서비스 실행 계정만 읽기 가능(`600`).

## Anti-pattern
- `core/` 서비스가 `firebase_admin` 직접 import
- 커밋 전 푸시 발송
- 푸시 실패로 측정값 저장 롤백
- 상태 변화 없는데 heartbeat마다 발송
- 무한 재시도 (백오프·상한 없음)
- 무효 토큰에 계속 재시도
- 발송 타임아웃 미설정
- 토큰 전체를 로그에 기록
- 서비스 계정 JSON을 repo에 커밋
- 안전 알림을 푸시 도달에만 의존
- 발송 이력 미기록 (실패 원인 추적 불가)

## Rule (규모에 맞춘 범위)
- Prometheus·Grafana·분산 트레이싱을 도입하지 않는다. Pi Zero 2W 512MB에서 수집 스택 상주 비용이 관측 이득보다 크다.
- 관측 수단은 3가지로 고정: 구조화 로그(journald), `/health` endpoint, DB에 적재된 수신·발송 이력.
- 지표가 더 필요해지면 DB 집계 쿼리로 먼저 해결한다. 별도 시계열 저장소 도입은 ADR로 결정한다.

## Rule (헬스체크 — 구성요소 분리)
- `/health`는 구성요소별 상태를 나눠 반환한다: `process`, `database`, `lora_radio`, `push`.
- `process` — 응답이 나가면 살아있음.
- `database` — 가벼운 `SELECT 1`. 무거운 쿼리 금지.
- `lora_radio` — 마지막 프레임 수신 경과 시간이 임계 이내인지. 무선 두절을 200 OK로 감추지 않는다.
- `push` — 최근 발송 실패율. 자격증명 만료를 조기에 드러낸다.
- liveness(프로세스 살아있음)와 readiness(요청 처리 가능)를 구분한다. systemd 재시작 판단과 앱 상태 판단은 다른 질문이다.

## Rule (상태 지표 — DB 기반)
- 수신 카운터: 성공·CRC실패·파싱실패·중복·미등록장비. 프레임 처리 경로에서 갱신한다.
- 장비별 마지막 수신 시각·RSSI·SNR. 통신 품질 저하를 여기서 본다.
- `seq` 기반 유실률. 안테나·거리·간섭 문제의 유일한 정량 지표다.
- 푸시 발송 시도·성공·실패 이력.
- 이 값들을 노출하는 내부 조회 endpoint를 둔다(`/internal/stats`). 앱용 공개 API와 분리한다.

## Rule (알람 조건 — 사람이 볼 것)
- 임계를 넘으면 무엇을 확인할지가 함께 정의돼야 한다. 조건만 있고 조치가 없으면 무시된다.
- 최소 조건 3개: ① 장비 무응답(마지막 수신 경과 > 임계) ② 유실률 급증 ③ 푸시 연속 실패.
- 조건은 설정값. 시연 환경과 벤치 환경에서 값이 달라진다.
- FAULT는 ALARM과 별개로 통지한다. 감지 불능을 정상으로 뭉개지 않는다.

## Rule (버전 추적)
- 부팅 로그와 `/health` 응답에 앱 버전(커밋 해시)과 현재 Alembic 리비전을 포함한다.
- 배포된 게 무엇인지 확인 못 하면 장애 원인 분석이 추측이 된다.

## Anti-pattern
- Pi에 Prometheus·Grafana 상주
- `/health`가 구성요소 구분 없이 항상 200
- `/health`에서 무거운 집계 쿼리 실행
- 무선 두절 상태인데 헬스체크 통과
- 수신 카운터·유실률 미기록 (통신 품질 추적 불가)
- 내부 진단 endpoint를 앱 공개 API와 같은 경로에 노출
- 임계 조건만 정의하고 조치 절차 없음
- `/health`·부팅 로그에 버전·마이그레이션 리비전 없음
- FAULT를 ALARM과 같은 경로로 뭉쳐 통지
